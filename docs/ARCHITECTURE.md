# Архитектура

## Сервисы

```
браузер ── nginx ──┬── frontend (React, статика)
                   └── api (Go) ──┬── PostgreSQL
                                  ├── llm_service (движок разговора) ── OpenRouter
                                  ├── asr_service (распознавание)    ── OpenAI
                                  ├── tts_service (озвучка)          ── OpenAI
                                  └── GPT Live: сервер выдаёт сессию,
                                      звук идёт браузер ↔ OpenAI напрямую
```

## Go API: модули

Монолит из модулей с жёсткими границами. Модуль читает и пишет только свою
схему базы; данные чужого домена берёт через Go-интерфейс, который связывает
`internal/app` (`adapters.go`). Нарушение границы роняет тест `internal/arch`.

| Модуль | Схема | Что внутри |
|---|---|---|
| `iam` | `iam` | организации, учителя, сессии, роли и права, ученики и их коды |
| `classroom` | `classroom` | классы и состав |
| `content` | `content` | уроки и версии: текст, лексика, цели, настройка аватара |
| `learning` | `learning` | назначения, выдачи заданий, попытки, разговор, аналитика |
| `live` | `ops` | сессии GPT Live и журнал голосовых соединений |
| `speech` | — | распознавание и синтез речи ученика через пулы шлюза |
| `lessonpipe` | `ops` | клиент к llm_service |
| `mlgw` | `ops` | пулы параллельности и учёт каждого вызова модели |
| `platform/*` | — | база, логи, ошибки HTTP, идентификаторы, миграции |

Зависимости между доменами идут в одну сторону: `learning → classroom` и
`learning → content`. Урок не знает, кому он выдан, класс не знает, какие
уроки в нём идут.

## Как идёт разговор с аватаром

1. Учитель назначает версию урока классу и выдаёт задания. Пока выдачи нет,
   ученик урока не видит.
2. Ученик открывает разговор. `learning` собирает бриф: текст урока, цели
   (фразы и грамматика), роль аватара, уровень, уже сказанное.
3. **Живой режим.** Сервер открывает сессию GPT Live с политикой из
   `internal/live/session.json` и правилами разговора по целям
   (`internal/live/conversation.go`). Звук идёт мимо сервера. Каждую фразу
   ученика браузер распознаёт через `/my/transcribe` и отправляет ответом;
   движок `llm_service` отмечает, что ученик употребил, и возвращает указание
   на следующий ход. Браузер добавляет указание в сессию.
4. **Голосовые сообщения.** Если живой режим недоступен, ответ аватара пишет
   движок (`/v1/conversation/turn`), а озвучивает `tts_service`.
5. На последнем ответе разговор закрывается, и фоновый разбор
   (`/v1/conversation/analyze`) отмечает по каждой реплике: цель зачтена,
   ошибка или пропуск. Из этих отметок строятся итог ученика и аналитика.

## Движок разговора (`llm_service`)

- `app/conversation/` — ходы, политика целей (`policy.py`), разбор
  (`analysis.py`), указания живой сессии (`live.py`), промпты (`prompts.py`).
- `app/levels/` — профили CEFR A1–C1 для указаний уровня.
- `app/languages.py` — языки разговора. Уроки MVP английские; на татарском
  написаны тесты логики разговора.

## База

Одна миграция `migrations/0001_schema.up.sql` со схемой целиком. Таблицы
событий (`learning.answer_events`, `learning.dialog_turns`,
`ops.pipeline_calls`) секционированы по неделям; секции вперёд создаёт
`public.ensure_weekly_partitions` — в миграции и раз в сутки из API.

## Настройки

`settings.py` — единый каталог умолчаний. `python3 settings.py --sync`
генерирует из него копии для Go (`internal/platform/settings`), Python-сервисов
(`*_settings.py`), Compose (`settings.compose.yml`) и политику голосовой
сессии (`internal/live/session.json`). `make check` проверяет, что копии не
разошлись.
